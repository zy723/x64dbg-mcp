# x64dbg-mcp v1.1.0-rc4 — 遗留 BUG 清零轮

**日期**: 2026-10-09
**前置**: commit 4cd45dc (rc3) — detach 崩溃修复
**范围**: rc3 遗留清单的全部 P0/P1 + 部署自动化升级

## 本轮修复

### Fix-A [P0] WaitForDebugging / WaitForPause 残留的 GUI 泵调用

rc3 只清了 Detach/AttachProcess 的 `PumpGuiMessages()`，这两个函数（attach 主流程必经）没动。当时理由是"两轮实测未崩"——但危险是结构性的：两个函数都在 HTTP/RPC 工作线程被调，PeekMessage/DispatchMessage 是 GUI 线程专属操作。

**修复**: 循环里删除 `PumpGuiMessages()`，纯 `sleep(10ms)` 轮询 `DbgIsDebugging()` / `DbgIsRunning()`（二者直读内部状态，无需泵）。`PumpGuiMessages()` 函数体+声明整体删除，代码库中已无任何调用点。

**回归**: attach 路径全链路重测——`debug_attach_pid` 一次成功（`state=running`），证明去泵化无副作用。

### Fix-B [P1] HTTP worker 可被慢客户端无限占用

`ReceiveHttpRequest` 的 `recv()` 循环无超时——半开/慢速客户端会永久钉死一个 worker 线程（HTTP 每连接一线程模型下表现为通道容量流失，实机现象即 MCP 客户端间歇 ETIMEDOUT 而 HTTP 探测正常）。

**修复**: accept 后立即设置
- `SO_RCVTIMEO = 30s` / `SO_SNDTIMEO = 30s`
- `SO_KEEPALIVE = 1`

慢客户端 30s 后被释放，不再累积占用。

### Fix-C [P1] 部署脚本端口写死 3000

deploy-and-test.ps1 硬编码 3000，实机配置是 3030，导致上一轮冒烟全灰。

**修复**: `Read-PluginPort` 自动读部署目录 `plugins\x64dbg-mcp\config.json` 的 `server.port`，兜底 3000。

### Fix-D [自动化] deploy-and-test.ps1 升级为全链回归

从"冒烟"升级为 12 步自动回归，单命令完成：构建(可选) → 杀 x64dbg → 装 .dp64（自动备份 .bak.prev）→ 重启 → 等就绪 → 验证 5 个新 tool 注册 → 复刻 detach 崩溃/W7 wedge/exit code 缓存/register+stack 全场景，任一步失败即 `throw` 并给出场景名：

```
Step 8: pause+DETACH (rc2 crash)   → x64dbg ALIVE 必须成立
Step 9: re-attach same PID (W7)   → 一次成功必须成立
Step 10-11: 强杀+缓存读回            → exit_code=cached 必须
Step 12: register_get_all/stack    → rip/rflags 有 + 占位字段无
```

## 本轮验证未修复项 — W10 乱码注释（说明）

尝试两种自动修复方案均验证失败：
1. GB18030 编码回环（PowerShell 实现）：产生**二次字节丢失**
2. GB18030 回环（Python surrogateescape 实现，tools/fix_mojibake.py 保留）：实测对 PluginEntry.cpp 修复 67 行后样本行为乱码——证实原始 `?`（U+FFFD）字符说明首次转码时字节已永久丢失，信息论上不可恢复。

**决定**: 保留 `tools/fix_mojibake.py` 作为半自动工具（对未损坏文件可正确双向）。损坏文件待人工按上下文重写注释——所有损坏行已在逐文件行号中列出（PluginEntry.cpp、BreakpointManager.cpp、BreakpointHandler.cpp 为 dense 区）。**不影响运行时任何行为**（纯注释）。
