# x64dbg-mcp v1.1.0-rc3 — detach 崩溃主机修复

**日期**: 2026-10-09
**前置**: commit 20b7cd3 (rc2) 装载后实测发现新 P0 级 bug
**严重级别**: P0 —— rc2 的 debug.detach 会把整个 x64dbg 进程杀死

## 问题现象

rc2 装载后测试序列：
1. init notepad → erun → attach_pid 成功 ✓
2. 调 `debug_detach` → MCP 返回 `success:true, debugging:false` ✓
3. **几秒后 x64dbg 进程消失**（tasklist 无 x64dbg；MCP server "not connected"）

## 根因分析

`DebugController::Detach()` 的旧实现（本会话 v1.1.0 新增）：

```cpp
ExecuteCommand("mcpdetach");     // ① 命令入 GUI 命令队列
while (IsDebugging()) {
    PumpGuiMessages();            // ② RPC 工作线程里泵 GUI 消息
    ...
}
```

叠加 `CmdMcpDetach`（GUI 线程命令 handler）里 `DetachProcessCore()`：

```cpp
ExecuteCommandDirect("detach");
Sleep(200);                        // ③ GUI 线程里硬等
if (IsDebugging()) {
    ExecuteCommandDirect("stop"); // ④ 强 stop —— debuggee 已死时二次触发
}
```

三个缺陷互相放大：

| 缺陷 | 机制 |
|------|------|
| ② 跨线程 Peek/DispatchMessage | RPC 工作线程不属于 GUI 线程，取不到 GUI 消息，却 DispatchMessage 空消息 + `GuiUpdateAllViews()` 跨线程刷视图，触发 x64dbg 内部竞态 |
| ③+④ GUI 线程 Sleep+嵌套命令 | 命令 handler 执行期间再 ExecuteCommandDirect("stop")，与 debug loop 的状态转换（EXIT_PROCESS 处理中）竞争 |
| 场景放大 | debuggee 被 taskkill 强杀后 x64dbg 内部仍在清理，此时 detach/stop 命令访问半清理状态 → 空指针/无效句柄 → 进程崩溃 |

[置信度：中] 具体崩在哪一行无法在无 dump 情况下确定；但 3 处跨线程/重入缺陷在 Windows GUI 程序中都是实锤违规，删除后崩溃消失，因果成立。验证方法：x64dbg Log 窗口或 WinDbg attach 到 x64dbg 观察 detach 时的 AV。

## 修复方案

核心原则：**RPC 工作线程只发命令 + 纯 sleep 轮询，绝不碰 GUI 消息泵**。

### 1. `DebugController::Detach()` (DebugController.cpp)

- `ExecuteCommand("mcpdetach")` → `DbgCmdExecDirect("detach")`：直接同步调 x64dbg 内置 detach，绕开 plugin 命令队列（不再进入 GUI handler 嵌套）
- 轮询循环删掉 `PumpGuiMessages()`，纯 `sleep_for(50ms)` 等 `IsDebugging()` 翻转

### 2. `CmdMcpDetach` (PluginEntry.cpp)

不再调 `DetachProcessCore()`（含 Sleep+嵌套 stop）。只 `DbgCmdExec("detach")` 入队，让 GUI loop 自然处理，立即 return。

### 3. `DetachProcessCore()` (DebugController.cpp)

- `ExecuteCommandDirect("detach") + Sleep(200) + ExecuteCommandDirect("stop")` → `DbgCmdExecDirect("detach")` + 无泵轮询 3s；超时才 `DbgCmdExecDirect("stop")` 兜底
- 此函数仍被 `AttachProcess` 的 detachIfBusy 路径从 RPC 线程调用，同样受益

### 4. `AttachProcess` detach-first 等待 + retry 路径

两处 `PumpGuiMessages()` 删除，纯 sleep 轮询；`ExecuteCommandDirect("stop")` → `DbgCmdExecDirect("stop")`。

## 验证结果（2026-10-09 实测，断点复现原始崩溃场景）

| 步骤 | 命令 | 结果 |
|------|------|------|
| 1 | `debug_init` + `erun` (notepad) | ✅ |
| 2 | `pause` + **`debug_detach`** | ✅ `success:true`，**x64dbg 存活**（上次 همین 步骤杀死 x64dbg） |
| 3 | debuggee 进程存活检查 | ✅ notepad 2388 未被杀（真 detach 语义） |
| 4 | **`debug_attach_pid`（同一 PID 重连，W7 场景）** | ✅ 一次成功 `state:running, rip` 返回 |
| 5 | `pause` + `taskkill /F` debuggee | ✅ CB_EXITPROCESS 在 **paused 状态**即捕获 exit_code=1 |
| 6 | `debug_get_exit_code`（stopped 后）| ✅ `exited:true, exit_code:1, cached:true` |
| 7 | `debug_init` 新 notepad + `pause` | ✅ |
| 8 | `register_get_all` | ✅ 18 项含 rip/rflags（rc2 修复回归通过） |
| 9 | `stack_get_trace` | ✅ 6 帧，占位字段已省略（rc2 修复回归通过） |
| 10 | `debug_stop` 收尾 | ✅ x64dbg PID 4456 全程存活 |

新 bug 未再复现：rc2 崩溃场景（detach → x64dbg 消失）在 10 步全链路中零复现。

| 文件 | 变更 |

| `deploy-and-test.ps1` (新增) | 自动部署：杀 x64dbg → 装 .dp64 → 重启 → HTTP 冒烟（注意：HTTP 端口是 **3030** 非 3000） |

## 遗留风险

1. **MCP stdio 通道偶发超时**：erun 等长命令后 stdio 有约 10-30 秒失联窗口（HTTP 3030 正常）。怀疑 MCP 客户端与 stdio 管道缓冲有关，与本次修复无关 [置信度：低]。**workaround**：长命令后改用 HTTP 3030 或等待重连。
2. `WaitForDebugging`/`WaitForPause`（attach 主流程）仍用 PumpGuiMessages——attach 路径两轮实测（rc2/rc3）未崩溃。它同样理论违规，但改动面大且无实测崩溃证据，**留给 v1.1.1**，避免无验证的激进改动 [置信度：高，防御性保留]。
3. debuggee 强杀后 state 卡 paused 直到手动 stop —— x64dbg 快照原生行为，非插件 bug。
